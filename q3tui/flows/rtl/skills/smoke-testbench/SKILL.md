# Smoke testbench

A smoke test answers one question: *does the design do its most basic job at all?* It is small on purpose; the verification flow does the
thorough work. You write it from the **spec, the requirements and the configuration only**. You must not read the RTL (it is denied):
a testbench derived from the code would only confirm the code.

## Choose the behaviours
Pick 3–6 behaviours, in this order of value:
1. **Reset**: after reset, outputs are at their reset values; the design comes out of reset cleanly.
2. **The main function once**: one legal input sequence and the result the spec states (a write then a read back, one transfer end to end,
   one computation with a known answer). Compute the expected value from the spec, by hand, in the testbench.
3. **A second, different input** of the same function (catches a hard-wired answer).
4. **One boundary** the spec names (full / empty, maximum length, last beat), only if the spec states the exact behaviour.
Tie each behaviour to the REQ ids it exercises. Skip anything the spec leaves open: do not guess behaviour.

## A design with registers on a bus
When the spec gives a bus (APB) and a register map, the registers are part of the basic function: drive the bus as the spec says (SETUP then ACCESS, wait for
PREADY), read every register's reset value, write then read back a read/write field, check a read-only field follows what the design drives, check a
write-1-to-clear field clears on writing 1. Use the register names, offsets and reset values of the **spec**, never of a generated file. If the design is
generated by the APB-CSR-Generator (the skill `apb-csr-tool` is listed), remember: only full 4-byte writes are accepted, a misaligned address answers PSLVERR
when `i_slverr_en` is 1.

## Write it so every simulator takes it
- One module `tb_smoke`, the design instantiated by the port names, widths and parameters the **spec** gives. Parameters get the values of the
  final configuration.
- Clock with `always #(PERIOD/2) clk = ~clk;` and a synchronous reset task. Drive inputs on the clock edge, sample after it; use `@(posedge clk)`,
  no `#` delays inside the checks, no `fork`/`join_any` games, no UVM, no classes, no `$urandom` unless the spec wants randomness.
- A watchdog: after a bounded number of cycles print a failure and `$finish`. A hang is a failure, never a pass.
- Check with explicit comparisons and print, for each behaviour, exactly one line:
  `SMOKE_RESULT <id> PASS` or `SMOKE_RESULT <id> FAIL <what was expected, what was seen>`. At the end `SMOKE_SUMMARY total=<n> failed=<n>` and `$finish`.
- Behaviour ids are short (`S1`, `S2`, …) and listed with their meaning and REQ ids in the plan you return.

## Iterate with the tools
`smoke_compile` compiles the testbench against the RTL and gives you the errors; `smoke_run` runs it and gives the result lines. A compile error
about a port or signal name means your reading of the spec's interface differs from the design: fix your side if the spec is clear; if the spec is
ambiguous, say so in `questions` (kind `spec_gap`) instead of adapting to the RTL.
